# GitFerry product capability and evidence matrix

Target directory authority remains local. Imported claims never authorize directory or
administrator changes; LDAP and AD qualification are tracked separately below.

This matrix is the auditable boundary between the product target and currently verified behavior.
It is not a feature wish list and a passing test count does not upgrade an individual row. The
reference integration target is Gitea 1.27.2, image digest
`sha256:d20286ca2b2e170fdf628e7231b8a31a3220ade39ff462b55041d43d1fc757dd`.

## Status contract

The three status columns use only these values:

- `supported`: the stated scope is implemented and has the required product-level evidence;
- `supported-with-limits`: a bounded implementation is evidenced and the limits in this row are
  part of the support contract;
- `not-supported`: GitFerry deliberately does not provide the behavior, or a probe established
  that the requested native behavior is unavailable through the selected interface;
- `not-checked`: no adequate test has established whether the behavior works;
- `blocked`: the planned evidence could not run because a named prerequisite was unavailable;
- `not-implemented`: the product path does not exist yet.

`Implementation` describes reusable application behavior. `First import` and `Return` describe
evidence for those two workflows independently. Module tests alone do not establish either workflow.
Every row has one owning roadmap issue; the owner closes the stated gap or accepts the bounded
capability at the named target release.

## Version and identity boundaries

Application versions, manifest schema versions and SQLite schema versions are independent. Manifest
v1 carries issues; Manifest v2 adds normal issue comments and an explicit parent-issue origin. v1
bytes and digests remain immutable. A native Gitea numeric ID is an instance-scoped replica fact,
not a portable object identity. Original timestamps stored with an origin are not restored native
Gitea timestamps.

The latest consolidated real-Gitea report contract is described in
[testing.md](testing.md#capability-claim-gate). Generated reports are run artifacts rather than
source-controlled proof substitutes; the verification documents bind the accepted claim to an
exact revision, Gitea pin and test entry point.

## Evidence execution baseline

The common `make test-integration` entry point, deterministic crash/lost-response synchronization,
required-evidence catalog, redacted failure diagnostics and run-scoped cleanup remain evidenced by
[the Linux integration verification](verification-linux-integration-run.md). Hosted pull-request
and integrated-main runs passed the stable `quality` and `gitea-integration` contexts; controlled
failure and watchdog dispatches remained red while retaining diagnostics and completing scoped
cleanup. These are test-system properties, not substitutes for an unsupported product row above.
